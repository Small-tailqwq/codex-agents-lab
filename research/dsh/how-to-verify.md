# 如何验证

分四层：冷检查（本仓库里跑，不连模型）→ 装配核对（隔离 profile 里看模型实际收到什么）→ API 单步基准 → 会话级
对照实验（真实模型、多步任务）。
前一层不过不进下一层。设计与取舍见 [设计 中文提示词控制](../designs/20261007-中文提示词控制.md)。

## 1. 冷检查

```sh
pnpm exec vitest run packages/bundles/zh-prompt-control   # 翻译守护 + 真实装配
pnpm exec oxlint packages/bundles/zh-prompt-control
pnpm --filter @smalltailqwq/dsh-zh-prompt-control run build
```

- `translations.spec.ts`：每条英文原文仍在 `vendor/deepseek-harness`（`mise.toml` 锁定的版本）源码里；真实的 0.2.1 系统提示词
  （`src/__tests__/fixtures/official-system-prompt.0.2.1.txt`）逐段全部被汉化；改一个字就不匹配。
- `plugin.spec.ts`：用上游真实的 `SystemPrompt` / `AgentLoop` 装配，核对规则段的位置、段落与运行时快照的汉化、
  锚点排在本步最后、续跑步不注入、三个配置开关。
- 升级 DSH 版本后先跑这一层：守护测试失败 = 上游改了措辞，按新原文更新 `src/translations.ts` 与夹具。

## 2. 装配核对（隔离 profile）

不碰 `desktop` profile。用 `web` profile（`dsh --profile web`）或另建一个：

1. `pnpm --filter @smalltailqwq/dsh-zh-prompt-control run build`，再在包目录 `pnpm pack` 得到 tgz（`publishConfig`
   把出口换成 `dist/`）。
2. profile 的 `package.json` 依赖加 `"@smalltailqwq/dsh-zh-prompt-control": "file:<tgz 绝对路径>"`，`dsh.profile.bundles`
   里登记包名，在 profile 目录装依赖后重启（link 方式见 dsh-skin-template 的
   `.agents/notes/implemented/install/2026-09-25-desktop-profile-release-age-and-local-link.md`）。
3. 新开会话发一句话，然后在会话日志里核对（`tool/eval-sessions.mjs --turns --since <今天>` 能定位会话）：
   - `system/message` 以「你是一个由 DeepSeek Harness 驱动的 AI 智能体。」开头，第二段是 persona，第三段是规则段；
   - 第 1 步的用户消息顺序：用户输入 → AGENTS.md → 运行时快照（中文）→ 技能目录 → **本包锚点**（最后一条）；
   - 工具续跑的步骤里没有锚点。

## 3. API 单步基准（不装插件）

[`tool/bench-api.mjs`](../../tool/bench-api.mjs) 从一个真实官方会话第 1 步取完整输入（系统提示词、工具目录、AGENTS.md、
运行时快照、技能目录），按 A / B / C 三组拼请求直接调 DeepSeek Messages API，只跑一步、不执行工具；B / C 的改写调用
`src/translations.ts` 与 `src/rules.ts`，与插件一致。S2 是真实两步：第 1 步模型自己调 `read`，原样回放它的思考块与
工具调用，再喂英文 README，度量第 2 步。

```sh
node tool/bench-api.mjs --context <官方会话 session.v4.jsonl.zstd> --readme <英文 README> --reps 3
node tool/bench-api.mjs --context … --model deepseek-v4-pro --effort high --scenarios S1,S5 --arms B
node tool/bench-api.mjs --summarize results.jsonl
```

PowerShell 里把逗号列表加引号（`--scenarios 'S1,S2'`），否则会被拆成数组。「正确」只是正则粗检（S1 有一次把
「转成同类型」判成未命中，人工看是对的；S2 的检查只看有没有中文正文），以人工抽查为准。

### 2026-10-22 工作区指令开场白：措辞还是位置

问题：官方工作区指令消息的开场白（"may be relevant to your work. Use them as guidance when applicable …"）会不会
削弱写在 `~/.dsh/AGENTS.md` 里的中文规则。底板同上（官方原版会话，不装本包），flash / max，S1、S2、S6、S7、S8
× 每格 4 次。各组都把 `~/.dsh/AGENTS.md` 换成同一份带语言规则的版本（`--agents-md`，内容是规则段「语言」前两条 +
现行 AGENTS.md，草稿不入库），不加规则段、不汉化：

| 组  | 开场白                                 | 思考以英文为主 | 其中 S6+S7 | 思考字数中位 | 提及规则均值 |
| --- | -------------------------------------- | -------------- | ---------- | ------------ | ------------ |
| H0  | 官方原文                               | 8/20           | 6/8        | 354          | 2.50         |
| H1  | 中文授权句（全局文件等同用户直接指令） | 10/20          | 7/8        | 385          | 6.15         |
| H2  | 同义英文授权句                         | 8/18           | 6/8        | 474          | 4.85         |

- 开场白怎么写都不影响语言：加强授权、换成中文、整段删掉，英文思考的比例都和官方原文一样。AGENTS.md 里的语言规则

  7634 → H1 11047。n=4，只是趋势；方向与 10-19 E 组「条款冗余拖长思考」一致。
- 结论：不需要替换开场白，回合锚点仍是必要的。K 与 H0 的差别有两处：锚点是本步最后一块（AGENTS.md 在用户输入之后、
  运行时快照与技能目录之前），锚点只讲语言且写明「思考从第一句起」；单步基准分不开这两者。AGENTS.md 只在第 1 步注入
  一次、长会话里越来越远，这一点单步基准测不到，要靠会话级实验。

### 2026-10-22 通道实验：同一组规则放在哪里、管得住什么

脚本 `drafts/bench-channels.mjs`（草稿，不入库），底板同上，flash / max，共约 1200 次调用，判定用 deepseek-v4-pro
（不开思考）加人工抽查。规则三条：语言、纠错不附和（不以「你说得对 / 好的 / 明白 / 收到 / 确实 / 抱歉」开头）、
表述（行话、「不是 X 而是 Y」、短回复不加标题）。各组 `~/.dsh/AGENTS.md` 换成去掉这三类规则的中性版，`~/.agents`
块去掉。分组：N 不加规则；AG 写进 AGENTS.md；SYS 写进系统提示词；ANC 每回合锚点；SA 系统提示词 + 锚点；CUR 现行
部署（插件规则段 + userRules + 汉化 + 现行锚点 + 现行 AGENTS.md）。

**语言**（思考以英文为主的比例，L1 问答 / L2 AGENTS 类任务 / L3 英文任务说明）

| ------------------------------------------------------------------------------------------ | -------------------------- | -------------------------------- |
| N 无规则                                                                                   | 18/18                      | 15/15                            |

| 「本轮的思考从第一句起就用简体中文（包括「这是一个……问题」这类开场判断）……」写进 AGENTS.md | 4/24                       | 23/35                            |
| 同一句写进系统提示词                                                                       | 12/23                      | —                                |
| 同一句作锚点                                                                               | 1/24                       | 2/36                             |
| 现行锚点去掉这一句                                                                         | 18/23                      | —                                |
| CUR 现行部署（只看 L3）                                                                    | 11/35                      | —                                |

关键检验：通用写法的锚点 30/48 对「从第一句起」锚点 1/24，p<0.0001；AGENTS.md 通用写法 14/17 对「从第一句起」4/24，
p=0.0001；AGENTS.md 第 1 回合 4/24 对第 5 回合 23/35，p=0.0002；第 5 回合 AGENTS.md 23/35 对锚点 2/36，p<0.0001；
CUR 对 CUR+AGENTS 句（L3）11/35 对 1/21，p=0.021。汉化、userRules、规则段内容、AGENTS.md 全文的差别都不显著
（X2 3/24、X3 2/24、X4 2/24、CUR 3/24 互相 p≥0.6）。

- 机制：flash 的思考以固定的英文模板开头（「The user asks / wants …」）。SA 组 30 次英文思考全部是英文开头，没有一次是
  中途切换；多步实验里第 1 步的语言延续到第 6 步（6 组 × 6 次 × 6 步，第 1 步中文的运行后面几乎都是中文）。所以起作用的
  是直接点名「第一句 / 开场判断」的那句话，泛泛的「用中文思考」不起作用。
- 通道：这句话放在 AGENTS.md 里第 1 回合有效，但只注入一次，几个回合后失效；系统提示词最弱；只有每回合的锚点稳定。
  语言必须靠锚点，AGENTS.md 加同一句可以补上英文任务说明（子代理）的缺口。
- 开场白措辞（上一节）、汉化、规则写在 MUST 还是「必须」，都不是主要因素。

**纠错与附和**

- 事实题上 flash 本来就不让步：用户说错（list.sort() 返回值、0.1+0.2、rebase 改 hash）时，N 组也全部坚持或先去验证，
  6 组 0 次让步。用户说的是自己的环境或记忆（「我明明启用了」「我记得是 jest」「白屏了」）时，N 组 24 次里 1 次在核实前
  认错；有规则的各组 0 次（CUR 在 E1 的 4 次「认错」是实验设计的问题：历史里助手声称读过文件却没有工具调用记录，
  中文思考的 CUR 发现后如实承认没读过，属于正确行为）。
- 附和集中在开头：用户说对时，N 组第 2 回合 5/7、第 5 回合 8/8 以「你说得对 / 是的…抱歉」开头；规则放在任一通道都压到
  接近 0（第 2 回合合计 2/141，p=0.0002；第 5 回合 AGENTS.md 1/8、锚点 2/8，对 N p≈0.001）。这条规则写在 AGENTS.md 里
  不随回合衰减。

**表述**

- 第 1 回合不加规则时 flash 格式很重（T1/T2 每条平均 5.8 个标题、15.8 处粗体）；任一通道的规则都把标题降到 0~~1.7、
  粗体降到 0~~4；SA 和 CUR 是 0 标题。行话 N 组 5/28 条回复出现，CUR 1/60（p=0.012）。
- 第 5 回合 N 组也不加标题了：前面几轮简短的回答本身就是示范，格式跟着对话历史走，规则主要管第一回合。
- 「不是 X，而是 Y」在单步回答里各组都很少（0~2 次），测不出差别；日志里的高频出现在长会话的总结性回复里。

**配置结论**：语言用锚点，锚点里必须有「从第一句起 / 开场判断」那一句（现行锚点已有），AGENTS.md「语言」一节写上同一句
补英文任务说明；附和、表述这类回复层面的规则写在 AGENTS.md 就够，不需要进锚点。

### 2026-10-22 汉化消融：汉化到底稳不稳中文思维链

起因：morlay 认为汉化系统提示词和注入提示词能让中文思维链更稳定，而 10-19 的 B/D 与本日的 X2/X3 都显示汉化没有边际作用。
差别在于那几组都带着「从第一句起」锚点，而本包汉化只覆盖系统提示词：底板里系统提示词英文词 1197 → 158，但工具目录的
4318 个英文词、技能目录和工作区指令开场白仍是英文。所以做 2 × 3：汉化（不汉化 / 本包汉化 / 全量汉化）× 规则（无 /
只有本包规则段 / 规则段 + 现行锚点）。全量汉化 = 本包汉化 + 工具与参数说明、技能目录、时间快照、开场白也用 v4-pro
忠实翻译成中文（`drafts/zh-full.json`，工具里剩下的英文只有工具名、参数名与 schema 关键字）。AGENTS.md 用中性版。
flash / max，第 1 回合（L1-L3）与第 9 回合（前 8 回合问答，R2L / R3L）每格 6 次，多步 M1 每组 5 次 × 6 步，共约 540 次调用。

| 规则 \ 汉化                     | 不汉化       | 本包汉化     | 全量汉化       |
| ------------------------------- | ------------ | ------------ | -------------- |
| 无规则：第 1 / 第 9 回合        | 18/18、12/12 | 16/17、12/12 | 15/16、12/12   |
| 只有规则段：第 1 / 第 9 回合    | 11/18、8/12  | 11/17、7/11  | **2/18、3/12** |
| 规则段 + 锚点：第 1 / 第 9 回合 | 1/18、1/12   | 0/17、1/12   | 2/17、0/12     |

（思考以英文为主的次数。）只有规则段时，全量汉化对不汉化：第 1 + 第 9 回合合计 19/30 对 5/30，p=0.0005；本包汉化对
不汉化 p=1.0。其余格子之间都不显著。多步 M1（中文任务、读英文文档）里 9 组都没有出现中途换语言（每次运行 6 步语言
一致，切换 0 次）：无规则的 3 组全程英文，有规则的 6 组第 2~~6 步全部中文，思考中文占比中位 0.86~~0.88，汉化与否差 0.02。

- 汉化本身不会让 flash 用中文思考：没有中文规则时，连全量汉化也是 15/16 英文。
- morlay 的说法在特定条件下成立：规则只写在系统提示词、没有「从第一句起」锚点时，**全量**汉化（主要是工具说明那 4000 多个
  英文词）能让规则生效，效果接近锚点。本包只汉化系统提示词，达不到这个效果。morlay 的规则句放在系统提示词、不带锚点
  （10-19 的 M0/M1/M2），正是这个条件。
- 有了锚点，汉化不再有边际作用；「更稳定」在多步里也测不出来：一旦第一句是中文，后面本来就不会切换。
- 取舍：锚点每回合一小段、不动提示词前缀；全量汉化要维护工具说明的译文，上游每改一个工具说明就要跟着改，也会让官方
  工具文档与模型看到的不一致。语言靠锚点；本包的段落汉化对语言没有可测的作用，留着不碍事；工具说明汉化不值得做。

### 2026-10-22 长会话漂移：为什么真实会话后段会变成英文 CoT

起因：一次真实会话（`D:\test\test1022-01`，三维 NS 爆破演示，不汉化、有规则段与锚点）主会话 106 步后段变成英文思考，
一个子代理第 1 步就是英文，另一个第 8 步起英文。单步与 6 步基准都没复现。逐项排查（统计按非代码行，代码与围栏块不计）：

| 假设 | 实验 | 结果 |
| --- | --- | --- |
| 锚点不是最后一块（真实 DSH 里锚点后面还有英文 time-context） | L1-L3 每组 10 次 | 锚点在后 6/28、在前 2/28，p=0.25，不是原因 |
| 步数长、上下文里英文多 | 30 步逐个读 23 份英文文档，三种汉化各 5 次 | 第 10 步起 0/94、2/101、1/105，不漂移 |
| 工具结果异常时转英文排查 | 写英文摘要任务，怪异工具环境对干净环境 | 反过来：干净环境漂得更多（53/126 对 23/118，p=0.0002）；异常结果后的下一步英文 28/220，正常结果后 158/464 |
| **模型自己持续写英文** | 30 步写英文摘要（每份读一篇写一篇） | 已写 0~2 份时英文步 3%，3~5 份 18%，6~8 份 24%，9~11 份 53%，12 份以上 64%（0~2 对 ≥9 p<1e-6） |

- 机制：思考里会起草要写进文件的英文内容。97 个英文步里 77 个首行是中文、随后起草英文摘要；写得越多，首行就是英文
  的步也越多。真实会话里 44 次写文件 43 次是英文（spec、README、代码，AGENTS.md「无约定时用英文」把文档默认成英文）。
- 汉化不影响：写英文任务里不汉化对本包汉化，怪异环境 23/118 对 30/124、干净环境 53/126 对 46/125，p 都约 0.44。
- 第 1 步就是英文的运行约占 1/6（各组 0~2/6，ZS1 1/6），一旦第 1 步是英文整次运行都是英文；子代理第 1 步英文属于这种。
  单次真实会话的「开不开汉化」对比会被它掩盖。
- 续跑步补锚点适得其反：每步在工具结果后追加一句「这一步也从第一句起用中文；英文内容直接写进工具调用」，第 1 步中文的
  运行里英文步从 128/344 升到 102/141（p<1e-6）；每 5 步补一次，英文步 58/173（p=0.44），只有首行英文降了（90/344 对
  28/173，p=0.011）。推测是工具结果后出现用户文本会被当成新一轮、前面的思考链不再回传（未验证）；本包「续跑步不追加」
  的做法是对的。
- 能做的：要写大量英文产物的任务接受思考里出现英文草稿；不需要英文产物的个人项目，把 AGENTS.md 的「无约定时用英文」
  改成中文能直接去掉这个诱因。
